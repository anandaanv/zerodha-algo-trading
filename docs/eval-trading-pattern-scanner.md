## Blocker #1 — License: CC BY-NC-SA 4.0 (NON-COMMERCIAL)
The license explicitly forbids commercial use. Algorithmic trading is inherently commercial. We cannot use this code in production, paper-trade against live brokers, or include it in any system that generates revenue. This alone is sufficient to disqualify the library.

## Blocker #2 — Detection logic is fundamentally flawed
The implementation does NOT detect structural chart patterns. It performs naive rolling-window comparisons that match almost any local extremum, regardless of pattern geometry.

### Example: `detect_head_shoulder` (tradingpatterns.py:5)
```python
mask = (high_roll_max > High.shift(1)) & (high_roll_max > High.shift(-1))
       & (High < High.shift(1)) & (High < High.shift(-1))
```
This flags any bar where the prior 3-bar rolling max is the previous bar's high. That's a **single pivot peak**, not a Head & Shoulders. A real H&S requires three peaks where the middle is highest, two shoulders at similar heights, and a defined neckline. None of that is checked.

### Example: `detect_triangle_pattern`
```python
mask_asc = (high_roll_max >= High.shift(1)) & (low_roll_min <= Low.shift(1))
         & (Close > Close.shift(1))
```
This flags any bar where price is making a higher close. That is an UP candle, not an ascending triangle. A real ascending triangle needs a flat upper resistance + rising lower support converging over multiple swings.

### Example: `detect_wedge`
```python
df['trend_high'] = df['High'].rolling(window=roll_window).apply(
    lambda x: 1 if (x[-1]-x[0])>0 else -1 if (x[-1]-x[0])<0 else 0)
```
Computes slope from first to last bar in a 3-bar window. Three bars with rising highs ≠ wedge formation. Real wedges have multiple swings with two converging trendlines.

### No pivot abstraction
The library has no concept of swing highs / swing lows / fractal pivots / ZigZag. All detection runs on raw OHLC bars via rolling windows. Real chart patterns are defined on swing structure, not single-bar masks.

## Blocker #3 — We already have better
Our codebase (Java, integrated with trading framework) contains:
- **CandidatePivotEngine** — leak-free walk-forward ZigZag pivots
- **TrendlineV2** — horizontal cluster (DBSCAN) + sloped line + retest state machine
- **HorizontalLevelDetector**, **SlopedLineDetector**, **TrendlineSignalEngine**
- **DTB / HNS / Triangle / Flag** detectors using structural pivot logic
- Full integration with strategy scanners, exit framework, paper/live execution

Adopting a Python library that detects patterns more crudely than what we have, while introducing cross-language IPC, would be a regression — even if the license allowed it.

## Stated accuracy is misleading
README claims 78-84% accuracy. From the source: accuracy is measured on **synthetic data** generated by `hard_data.py`. Synthetic OHLC ≠ real-market microstructure. The conditions used to generate the synthetic series likely match the conditions used to detect them, leading to circular validation.

## What CAN we learn from it
The repo's *enhancement* path (Savitzky-Golay filter, Kalman filter, wavelet denoising for price smoothing before pattern matching) is interesting as a *technique*. We could consider adding optional smoothing to our existing pivot detection, but this is a minor enhancement to our own engine, not a reason to adopt this library.

## Recommendation
**Close this evaluation. Do not pull the library. Continue improving our existing pattern detection.**

If chart patterns are a current gap, the right path is:
1. Identify which specific pattern coverage is missing in our Java codebase (DTB ✓, HNS ✓, Triangle ✓, Wedge ?, Channel ?, Flag ✓)
2. Extend our existing detectors with the missing patterns using our pivot/trendline framework
3. Validate with real market data using our existing simulation harness
